# WorldGen

Детерминированный сферический мир на C# из [манифеста](./WorldGen.md). Основной сценарий — начальная эпоха; региональная карта и отдельный региональный сервер сняты с эксплуатации. Старое ядро сохранено только для регрессионных тестов.

Ресурсное многообразие: 24 растения, 8 животных, поиск посадочного материала, опытные посевы, сезонный урожай, сады, живой отлов и стада, промысловые лагеря. Механизмы и ограничения: [BIOSPHERE.md](./BIOSPHERE.md). Итоги большого прогона: [BIOSPHERE_RUN.md](./BIOSPHERE_RUN.md).

Редактор сети технологий: `/technologies.html` — ноды и типизированные связи, ручные мысли, очередь `manual` и журнал поэтапного внедрения. Реализованная часть хранится в истории, остаток остаётся в работе. Черновики не меняют симуляцию. Управление, файлы и процедура адаптации: [TECHNOLOGY_EDITOR.md](./TECHNOLOGY_EDITOR.md).

Потребности домохозяйств: фактический рацион, приобретённые привычки, вода, качество жилья и свободное время влияют на занятия и строительные решения. Правила находятся в `wellbeing` каталога поселений. Формулы, миграция, проверки и границы первого среза — [WELLBEING.md](./WELLBEING.md).

Точная гидрология 1:1, кеш и схема годового обновления — в [HYDROLOGY.md](./HYDROLOGY.md). История согласования берегов и исправления «домов под водой» — в [CARTOGRAPHY.md](./CARTOGRAPHY.md).

## Запуск

Новый независимый стартовый мир: **6 поселений, 510 жителей**, общий каменный набор, разные начальные навыки, сезонный календарь, зимняя заготовка, погода и её хозяйственные последствия. Запуск: `dotnet run --project src/WorldGen.Server -- --urls http://127.0.0.1:4175 --sphere-scenario primordial`, карта — `http://127.0.0.1:4175/sphere.html`. Основной запуск теперь только сферический; старые миры перенесены в архив. Описание: [PRIMITIVE_WORLD.md](./PRIMITIVE_WORLD.md), [WEATHER.md](./WEATHER.md). Оползни пока только специфицированы: [LANDSLIDES.md](./LANDSLIDES.md).

Требуется .NET SDK 10. Node.js 24+ нужен для тестов отображения и npm-команд.

```powershell
npm test
dotnet run --project src/WorldGen.Cli -- --sphere-scenario=primordial --days=3650 --progress --report=TestResults/run.json --save=TestResults/world.json
npm run visualize
```

`--days=` задаёт продолжительность; `--seed=` позволяет проверить другой рельеф. Каталог мира доступен в `/api/sphere/catalog`.

### Политика миров во время разработки

После изменения технологий, правил или структуры состояния запускается новый мир и выполняется контрольный прогон на 3650 дней. Миграции между разными отпечатками контента до появления реального игрового процесса не поддерживаются: несовместимый снимок отклоняется. Снимки той же версии по-прежнему восстанавливаются точно и используются для воспроизводимости и проверки продолжения симуляции.

`npm run visualize` запускает только сферический C#-мир по адресу `http://127.0.0.1:4175`. `/` и `/index.html` ведут на сферу; старые региональные API удалены.
Карту можно масштабировать колесом или кнопками, перемещать перетаскиванием и вернуть целиком кнопкой «По размеру». После короткой неподвижной задержки наведение показывает данные зоны; щелчок фиксирует её подробности под картой.
Основной слой оформлен как топографическая карта: поверхность рисуется векторно на текущем масштабе, микросетка скрыта, высота показана горизонталями через 10 метров и отметками высот, лес — границами и условными знаками, дороги — плавными линиями. На общем масштабе границы поселений берутся из нод 10 × 10, при приближении уточняются до зон и сглаживаются.

## Миграция ядра на C#

Основное исполняемое ядро перенесено на .NET 10. C# загружает и валидирует тот же внешний контент, воспроизводит генераторы случайных чисел, строит пространственную иерархию, выполняет полный дневной конвейер и сохраняет/восстанавливает снимки. Контрольные SHA-256 побайтно совпадают с JS на днях 0, 1, 30, 365 и ежемесячных точках многолетнего прогона.

```powershell
dotnet restore WorldGen.slnx
dotnet build WorldGen.slnx --no-restore
dotnet test WorldGen.slnx --no-build
dotnet run --project src/WorldGen.Cli --no-build -- --sphere-scenario=primordial --days=120
dotnet run --project src/WorldGen.Server --no-build --urls http://127.0.0.1:4175
```

Основной API: `/health`, `/api/sphere`, `/api/sphere/catalog`, `/api/sphere/chunks/{face}/{x}/{y}`, `/api/sphere/simulation`, `POST /api/sphere/step?days=30`, `/api/sphere/simulation/snapshot`. JS-эталон и прежние сценарии оставлены как регрессионный оракул, не как второй работающий мир.

## Сферическая карта

Новая пространственная основа — cubed sphere: шесть квадратных граней по 416 × 416 зон, каждая зона по-прежнему состоит из двух треугольников. Получается 1 038 336 зон и 2 076 672 треугольника без полюсной сингулярности и без ложного тороидного замыкания. Грани делятся на чанки 32 × 32; базовые высота, климат, биом, лес и стоимость прохода генерируются по 3D-координате сферы, поэтому процедурный сигнал непрерывен на швах.

```powershell
dotnet run --project src/WorldGen.Cli --no-build -- --sphere-summary
```

Конфигурация лежит в `content/worlds/cube-sphere-prototype.json`. Полный базовый рельеф занимает около 25 МиБ в плотных массивах; History Delta, тропы, постройки и локальные знания хранятся разреженно только для изменённых зон.

Вращаемый просмотр доступен по адресу `http://127.0.0.1:4175/sphere.html` (это основной интерфейс проекта). Обзор использует LOD 1:4; от 3,5× загружаются видимые точные чанки 32 × 32. В клиентском кэше не более 192 чанков, одновременно выполняются не более четырёх запросов. Обзор и чанки содержат неизменяемый процедурный рельеф. Шаг симуляции не сбрасывает чанки и не запрашивает обзор заново.

Изменения леса, владений и построек передаются в поле `map` ответа симуляции; отдельный `GET /api/sphere/map` служит для синхронизации после изменения угодий. Лес — разреженный замещающий снимок всех отклонений от процедурной базы, поэтому пропущенный ответ не ломает последовательность. Границы и постройки передаются только при изменении `mapClaimsRevision`; клиент также отправляет `mapWorldId`, защищающий от смешивания разных запусков сервера. Поздние ответы не откатывают более новое состояние. Возврат леса к исходному значению удаляет переопределение.

Горизонтали кешируются отдельно от леса и границ. Версии геометрии зависят от локальных данных и соседних участков для сглаживания, не от номера дня. Озёрная/морская заливка, береговая обводка и маска воды строятся по одному пиксельному краю, без отдельного упрощённого векторного берега. При неизменных камере и видимых данных повторно используется пиксельная подложка. Счётчики запросов чанков, построения рельефа/среды и подложки позволяют проверить работу кеша.

Перетаскивание захватывает поверхность, включая переходы через полюса. Колесо приближает к точке под курсором до 64×; двойной щелчок центрирует выбранное место. Списки «К поселению» и «Площадка» позволяют быстро перейти к зданиям и угодьям. На близком масштабе видны их контуры и точные данные зоны.

Топографический слой использует светлую картографическую подложку, интерполяцию высоты/растительности, сглаженные берега и границы влияния. Векторная геометрия строится в координатах мира, сглаживается до проекции и кешируется по участкам с перекрытием на стыках. Перемещение камеры только проецирует существующие линии и знаки; экранной конкуренции между деревьями и подписями больше нет. Кеш перестраивается при изменении исходных данных/LOD, а не при искривлении проекции. Водное поле также не зависит от камеры: только его экранное сглаживание и обводка пересчитываются на текущем разрешении, совместно с заливкой. Гидрологическая точность озёр — 1:1; берег следует знаковой высоте относительно уровня воды (подробнее в [HYDROLOGY.md](./HYDROLOGY.md)). Горизонтали имеют сечение 100/50/20/10 м, каждая пятая утолщена. Высоты абсолютные в системе модели; уровень моря задан в конфигурации (сейчас 62 м). Интерполяция относится только к изображению: клики, строительство и влияние используют точные зоны. Реки и горизонтали отсекаются маской тех же пикселей воды, что используются в подложке, включая небольшие озёра.

Векторные SVG-контуры и палитра вынесены в `visualizer/assets/topographic-symbols.json`; один каталог используется Canvas-картой, легендой и страницей `/topographic-atlas.html`. Это авторская адаптация [топографических принципов USGS](https://www.usgs.gov/educational-resources/topographic-map-symbols), не точное соответствие ГОСТ/USGS. Знаки леса привязаны к мировой решётке и seed; перемещение камеры не меняет их координат. Типы деревьев пока декоративные обозначения леса, а не отдельные виды в симуляции. На близком масштабе показываются реальные постройки и угодья; контур площадки не равен плану стен. Дороги, тропы и мосты подготовлены в каталоге, но не рисуются без объектов модели.

`GET /api/sphere/hydrology` публикует статический водосборный слой: priority-flood на 6 × 416 × 416 отсчётах (**1:1**), заполнение впадин до перелива, выбор уклона стока с диагональными соседями и накопление условного стока по влажности. Вклад зоны уменьшен в 16 раз относительно прежней сетки 1:4, чтобы сохранить масштаб стока. Граф пересекает швы сферы, не имеет циклов и сохраняет суммарный сток. Видимые русла разделены у озёр, а внутренняя гидрологическая связь сохраняется. Берег интерполируется по знаковой высоте относительно уровня озера, не по квадратной маске. Список «Местность» ведёт к речным участкам. Поток — условный сигнал, не м³/с; площади ячеек пока не взвешены по сферической метрике. Сезонный водный баланс и эрозия ещё не реализованы. Бытовой слой использует ту же пресную воду для снабжения, рыбу — для добычи, а водные клетки исключает из сухопутных путей. Слой рассчитывается один раз при запуске и хранится в памяти; годовые частичные обновления пока описаны как контракт в `HYDROLOGY.md`. При изменении гидрологии создаётся новый мир.

Для проверки связи «использование земли → производство и границы» можно выбрать угодье и прекратить/возобновить его использование. Операция `POST /api/sphere/land-use/{id}?usage=0..1` меняет загрузку связанного производства при следующем дне и пересчитывает влияние. Пока это ручная команда, не автономное решение экономического агента. Изменения хранятся в памяти сервера; перезапуск восстанавливает исходный контент. Экономика старого регионального сценария этим действием не изменяется.

### История бытового слоя: прежний сценарий foragers

Содержание и обновление: два вида износа домов/колодцев, платный ремонт и разбор, материалы с разной долговечностью, конечный запас воды и восстановление залежей. Настройки — `lifecycle` в правилах поселений; устройство и границы модели — [LIFECYCLE.md](./LIFECYCLE.md). Поля на топографической карте объединяются в мягкие контуры без внутренней клеточной сетки.

Сервер по умолчанию запускает три стоянки охотников-собирателей, 490 жителей. Жильё ограничено вместимостью (25 человек на жилой слот, 100 на полностью жилую зону). Домохозяйства добывают пищу, воду, топливо и материалы, осваивают ремесло; строительство и промышленность используют тот же бюджет труда. Реальные походы формируют тропы. Выгодные колодцы и недостающее жильё строятся за материалы и время, возможны локальные переезды и забрасывание зданий. Возобновляемые природные запасы отделены от конечных месторождений.

Правила: `content/worlds/settlement-rules.json`, старт: `content/worlds/spherical-foragers.json`. Механика, проверки и оставшиеся ограничения подробно описаны в [SETTLEMENTS.md](./SETTLEMENTS.md). Панель «Поселения: быт и развитие» показывает снабжение, труд, навыки и причины решений. Старый сценарий ниже доступен с `--sphere-scenario early_iron`.

Слой «Снабжение и разведка» оценивает устойчивое ухудшение условий и может отправить небольшую группу с оплаченным трудом и провизией. Разведчики проходят реальный сухопутный маршрут, возвращают остатки запасов и только после возвращения передают датированные сведения. Благополучная стоянка не расширяется по таймеру. Основание новых поселений и сезонная ёмкость угодий — следующие этапы; верхняя оценка природного восстановления ещё не равна гарантированной добыче.

Новые дома, колодцы, огороды и местные переезды проходят через «Совет поселения»: домохозяйства накапливают угасающую поддержку, выбирают место и дают разрешение платной подготовке. Компетентность и отложенная оценка использования меняют вес участия. Полная схема — [DECISIONS.md](./DECISIONS.md). Дичь перемещается и уходит от охотников, большой запас рыбы не отменяет трудности лова, а расчистка и добыча уменьшают лес. Огороды требуют земли, труда и срока роста; жильцы переселяются частями. Правила и ограничения — [SUBSISTENCE.md](./SUBSISTENCE.md), параметры — `subsistence` в JSON. На карте есть отдельный слой «Дичь · подвижные зоны (наблюдатель)».

### Первый сферический экономический сценарий — сохранён для сравнения

`content/worlds/spherical-economy.json` отдельно задаёт объединение шести региональных экономических шаблонов в три сферических поселения, население и абстрактные торговые связи. Используется тот же `SimulationEngine`, без параллельной упрощённой экономики: 17 предприятий / 15 рецептов, технологии, институты, потребление, поставки, демография, кризисы и причинный журнал. Производственные площадки выбираются по реальным сферическим данным; состояния материализованы только для примерно 3 тысяч занятых/используемых зон, а не миллиона объектов.

На сфере доступны `+1 день`, `+30 дней`, запуск/пауза, переход к производству и панель «Экономика и события». Лесозаготовки меняют `NaturalState`, передаваемый в динамический слой карты; ручное выключение поля обнуляет загрузку его производства. API: `GET /api/sphere/simulation`, `POST /api/sphere/step?days=1..365`, `GET /api/sphere/simulation/snapshot` (экспорт). Отдельная региональная симуляция больше не запускается. Снимок можно восстановить при запуске: `dotnet run --project src/WorldGen.Server -- --sphere-snapshot C:\path\snapshot.json` (для раннежелезного мира также `--sphere-scenario early_iron`). Проверяются сценарий, отпечаток контента и набор сферических участков; несовместимый снимок останавливает запуск. Импорт через интерфейс и автоматическое сохранение пока не реализованы.

Это первый перенос, не физически откалиброванный сценарий: маршруты ещё абстрактные, не дороги по клеткам; площадь и природные потенциалы требуют калибровки. Использование крупных угодий не управляется автономно. Тестовая водяная мельница не имеет доступной площадки у реки и явно заблокирована, а не производит без воды. Регрессии прежнего переноса проверяют 120 дней, детерминизм, истощение леса и отключение поля; новый бытовой слой имеет отдельные тесты.

## Граница данных и состояния

Редактируемый контент находится в `content/`:

* `resources.json` — виды ресурсов;
* `recipes.json` — производственные рецепты;
* `technologies.json` — определения технологий и типизированные связи графа;
* `maps/` — параметры процедурной сетки, рельефа и населения;
* `scenarios/` — города, маршруты, начальные запасы и запланированные воздействия.

Малые ремесленные преобразования развивающихся поселений задаются отдельно в `primitive.processes`; схема расширения и граница с региональными предприятиями описаны в [`SETTLEMENT_PROCESSES.md`](./SETTLEMENT_PROCESSES.md).

Семантика ID и рёбер технологического графа описана в [`content/README.md`](./content/README.md).

Каждый файл содержит `schemaVersion`, а все сущности имеют стабильные строковые ID. Ссылки и допустимые типы связей проверяются при загрузке.

Состояние мира сохраняет версии схем и SHA-256-отпечаток всего набора контента. Изменённые определения поэтому нельзя незаметно принять за прежнюю версию мира.

Определение технологии отделено от состояния её освоения. Внешний граф описывает существующие знания и связи между ними. Показатели `Knowledge`, `Competence`, `Capability` и `Adoption` принадлежат конкретному миру, региону или организации и должны храниться в снимке симуляции.

Правила расчёта остаются кодом. JSON не должен постепенно превращаться в плохо проверяемый язык программирования.

* пищевые и топливные потребности населения, порчу запасов, сезонность и локальные цены;
* локальные торговые намерения с информационной задержкой и последующим подбором маршрута;
* время доставки и пропускную способность маршрутов;
* единое состояние дороги: обслуживание и трафик меняют её состояние, а оно одновременно влияет на торговлю и скорость курьерских сообщений;
* автономные решения советов и гильдий о резервах и производственных мощностях;
* медленную демографию, здоровье и миграцию при продолжительном дефиците;
* эндогенный риск эпидемии из плотности, болот, здоровья и транспортных связей;
* распространение дефицита с задержкой;
* причинный журнал и контрольный хеш состояния;
* сериализацию снимка с состояниями потоков случайных чисел и точное детерминированное продолжение истории;
* граф из 15 знаний и отдельные состояния Knowledge, Competence, Capability и Adoption;
* перенос знания и сообщений между поселениями с физической задержкой;
* целостность внешнего технологического графа;
* сборку городов из территориальных фрагментов;
* событийное разворачивание и сворачивание городских нод;
* сохранение значимых личностей вне временного detail overlay.
* иерархию из 10 000 зон → 100 укрупнённых нод → 1 региона;
* две треугольные половины зоны и общие детерминированно искажённые вершины;
* изменяемый History Delta природных площадок: качество почвы, лесная биомасса, рыбный запас и месторождения;
* интерактивную изометрическую карту в трёх масштабах и слои биомов, высоты, влажности и природных ресурсов.
* замкнутую cubed-sphere топологию примерно на миллион зон с обратимыми переходами между гранями;
* чанковый непрерывный 3D-генератор сферического рельефа без материализации миллиона объектов;
* клеточные тропы, которые усиливаются трафиком, снижают стоимость пути и постепенно исчезают без использования;
* строительную вместимость зон, связные многоклеточные постройки и технологическое повышение плотности;
* динамическое влияние города от реальных построек и используемых угодий;
* локальное распространение технологии, где внедрённая практика передаёт знание намного сильнее одной осведомлённости;
* кэшируемое исполнение вложенных нод со стабильными входными коридорами, событиями и плановым пробуждением.

## Осознанные ограничения

Это проверочный каркас, а не готовая экономическая модель.

* цены являются локальными сигналами дефицита и влияют на подбор сделок, но денег, собственности и бюджетов ещё нет;
* пропускная способность маршрута резервируется в день отправки, а не на каждый день движения партии;
* поселения самостоятельно публикуют намерения, но их сопоставляет единая региональная биржа без конкуренции перевозчиков;
* производственная мощность пока является агрегатом предприятия и не включает здания, собственников и отдельные заказы;
* эндогенные эпидемии уже возможны, но санитария и конкретные болезни пока представлены сводными факторами;
* причинный журнал растёт линейно (десятилетний эталонный прогон создаёт около 84 тысяч записей); ежедневная телеметрия уже ограничена двумя годами, но свёртка старой причинной истории ещё не реализована;
* развёрнутая городская нода пока создаёт структурный overlay, но не переключает экономику на более детальный алгоритм;
* старая плоская контрольная сцена всё ещё использует вычисленные при создании границы; на сфере есть автономный бытовой цикл строительства, но расширение землепользования и пространственная межгородская логистика ещё не замкнуты;
* эндогенный генератор пока моделирует только эпидемический риск; войны, политические конфликты, пожары и природные катастрофы ещё отсутствуют;
* природное восстановление и истощение уже являются состоянием площадки, но пока не меняют биом, русло реки или границы поселений.
* размер зоны 100 × 100 м пока номинальный: радиальная проекция cubed sphere даёт небольшую разницу площадей между центром и углами грани; перед физической калибровкой планеты нужны метрика площади/расстояния и решение, требуется ли equal-area-проекция;
* сферическая гидрология имеет глобальный ациклический граф стока и озёрные берега на сетке 1:1; метрические площади водосборов, сезонный водный баланс, годовой пересчёт изменённых бассейнов, эрозия и бродовые переправы пока не реализованы.

Текущая декомпозиция и следующие этапы описаны в [`ROADMAP.md`](./ROADMAP.md).
